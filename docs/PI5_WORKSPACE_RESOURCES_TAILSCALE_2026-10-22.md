## 1. 추적 번호가 1800까지 증가해도 1800명을 보관하는 것은 아니다

Hailo/EdgeFall의 `track_id`는 `uint64_t next_id_++`로 발급되는 **임시 추적 번호**다.
얼굴 등록 DB의 person ID나 고유한 실제 사람 번호와 다르다. 같은 사람도 가림·이탈로
추적이 끊어지면 새 번호를 받는다. 서비스 재시작은 이 카운터를 다시 시작한다.
카운터 자체는 고정 크기 정수이므로 숫자가 크다는 이유로 메모리가 계속 늘지 않는다.

추적을 주기적으로 리셋하면 진행 중인 관절 이력/낙상 판단이 끊어진다.
따라서 자동 리셋이나 번호 재사용은 추가하지 않았다. 대시보드의 설명을
`현재 임시 추적 번호 (등록자 ID 아님)`으로 바꿨다.

### 실제 수명·상한 조사

| 대상 | 확인한 동작 |
|---|---|
| native 사람 track | 미검출 8프레임 초과 시 삭제, unique_ptr 해제 |
| 시간 분류기 | 약 3.13초 입력 창 + 약 0.5초 보간 여유, 오래된 항목 pop_front |
| RTSP 표시 입력 | leaky latest-frame queue 및 appsink 최대 1프레임 |
| Hailo 내부 큐 | 각 단계 1~수 프레임 제한; 앱은 최신 프레임만 공급 |
| Python 지연/FPS 통계 | deque 최대 120개 |
| 최근 화면 이벤트 | deque 최대 100개 |
| 진단 쓰기 대기열 | 최대 256개, 가득 차면 AI를 막지 않고 누락 수 표시 |
| 진단 파일 | 기본 파일당 20MB, 백업 2개 회전; 점검 당시 전체 약 46MB |
| 낙상 중복 방지 track→event 기록 | 기존 무제한 → **최근 256개로 제한** |
| Paho QoS 발행 대기열 | 기존 기본 무제한 → **256개로 제한** |

실제 동작 중인 Pi5 PID 54620을 약 5분 간격으로 확인했을 때 RSS는 모두
526,016KiB(약 514MiB), 스레드 51개였다. 전체 메모리 여유는 약 6.4GiB,
swap 사용 0이었다. 당시 API에는 ID 189/246의 약 2개 track이 있었다.
이 점검에서는 전반적인 메모리 누적 증거를 확인하지 못했다. 장시간 누수 부재를
보증하는 결과는 아니며, 코드에서 발견한 두 무제한 보관 지점만 제한했다.

MQTT 발행 함수가 오류 코드를 반환하면 `MQTT_EVENT_REJECTED` 로그와
`/api/status.mqtt_rejected_events`를 증가시킨다. 개발자 상세에도 표시한다.
이 값은 **발행 시도 거부 수**이며, 연결이 끊겨 애초에 발행하지 않은 모든 이벤트의
영구 보관 수가 아니다. MQTT 단절 중 이벤트를 나중에 안전하게 재전송하는 durable
outbox는 아직 별도 과제다. 대기열 상한 때문에 실패한 경보를 성공으로 주장하지 않는다.

## 2. 얼굴 등록 방향: 원본 영상 좌표와 거울 좌표 분리

기존 화면은 비반전 카메라 영상에 '화면 좌우' 안내를 붙였다. 사용자가 느끼는
본인 좌우와 화면 좌우가 달라 혼동할 수 있었다.

새 얼굴 등록 탭은 **깨끗한 원본 스트림을 브라우저에서 좌우 반전**해 거울처럼 보여준다.
영상 원본, 얼굴 모델 입력, 저장된 특징은 뒤집지 않는다. 일반 모니터 탭의 이름·박스
영상도 기존 방향을 유지한다.

| 내부 yaw/기존 template key | 거울 미리보기 방향 | 사용자 안내 |
|---|---|---|
| front | front | 정면 |
| right (원본의 +X) | left | ← 내 왼쪽 |
| left (원본의 -X) | right | 내 오른쪽 → |

API에 `display_direction`을 별도로 제공한다. 기존 얼굴 템플릿의 이름을 뒤집거나
데이터를 다시 쓰지 않았다. 그림, 화살표, 안내문, 방향별 수집 수를 같은 기준으로 맞췄다.
현재 실물 카메라가 책상 아래를 향한 상태였으므로, 올바른 얼굴 구도에서 본인 좌우를
따라가는 최종 사용자 시험은 필요하다.

### 더 깊은 측면·뒤쪽 등록은?

현재 YuNet은 눈·코·입 landmark를 이용하고 SFace는 이를 정렬한 얼굴 특징을 비교한다.
눈과 코가 가려지는 후측면/뒤통수는 이 경로에 신뢰할 입력이 아니다.
등록 각도 수만 늘리거나 품질 기준을 낮춰도 보이지 않는 얼굴 특징은 복원되지 않는다.

이번에는 품질 기준을 낮추거나 후측면 템플릿을 추가하지 않았다. 다음 단계라면
얼굴이 보이는 범위 내의 더 다양한 사선 표본을 별도 템플릿으로 보관하고, 각도별
동일인/타인 검증 후 적용한다. 360도 3D 스캔·위변조 방지로 표현하면 안 된다.

## 3. 실제 탭 전환과 영상 부하 정리

상단 `실시간 모니터 / 얼굴 등록 / 감지 기록`은 스크롤 링크가 아니라
하나의 패널만 보이는 탭으로 변경했다. URL hash로 직접 진입·뒤로 가기도 가능하다.
키보드 좌우/Home/End 이동, aria-selected/tabpanel 연결을 적용했다.

- 모니터: Dahua 및 Camera Module 3의 분석 결과, 스피커 시험, 개발자 상세.
- 얼굴 등록: 거울 미리보기와 등록/관리 UI만 표시.
- 감지 기록: 최근 이벤트만 표시, 영상 연결 없음.
- 등록 중 다른 탭으로 이동하면 해당 등록 세션에 취소 요청.
- 숨겨진 탭의 MJPEG 연결을 끊는다. 탭이 숨겨져도 카메라 분석·낙상 MQTT는 계속 실행.
- 브라우저 전체가 백그라운드로 가도 영상 연결을 정리하고 복귀 시 재연결.

실제 Chromium에서 다른 시청자가 없는 조건으로 확인한 서버 연결 수:

| 화면 | cam3 오버레이 / 원본 | Dahua 오버레이 / 원본 |
|---|---:|---:|
| 모니터 | 1 / 0 | 1 / 0 |
| 얼굴 등록 | 0 / 1 | 0 / 0 |
| 감지 기록 | 0 / 0 | 0 / 0 |
| 탭 반복 전환 후 감지 기록 | 0 / 0 | 0 / 0 |

이는 영상 전송·JPEG 표시 부하 감소다. 영상 지연 전체가 0이 됐다는 뜻은 아니다.

## 4. 시스템 / 라이트 / 다크 테마

우측 상단 선택기를 추가했다. 기본은 브라우저/OS의 `prefers-color-scheme`이며,
시스템 모드에서는 OS 색상 설정 변경을 즉시 따른다. 수동 선택은 localStorage에
저장하고 새로고침 후 유지한다. 테마 적용 스크립트를 CSS보다 먼저 로드해 밝은 화면이
잠깐 번쩍이는 현상을 줄였다. 390px 폭에서도 세 탭과 테마 선택이 보이도록 조정했다.

Pi4 협업자 화면의 테마는 변경하지 않았다.

## 5. Flask에 대한 판단과 다음 운영 단계

**Flask 프레임워크는 현재 상태 API·얼굴 등록·작은 대시보드에 계속 사용할 수 있다.**
그러나 현재 `app.run(threaded=True)`의 내장 개발 서버를 운영 서버로 확정해서는 안 된다.
공식 문서도 운영 환경에는 전용 WSGI 서버를 사용하도록 안내한다.
[Flask 운영 배포 문서](https://flask.palletsprojects.com/en/stable/deploying/),
[Flask의 Gunicorn 안내](https://flask.palletsprojects.com/en/stable/deploying/gunicorn/).

다음 구조를 권고하되, 이번 요청은 적합성 검토이므로 실행 서버 자체는 바꾸지 않았다.

1. Hailo·카메라를 소유하는 추론 프로세스는 하나만 둔다.
2. API/화면은 전용 WSGI 서버로 운영하고 추론 생명주기를 명시적으로 관리한다.
3. 일반 웹 서버 예제의 worker 수를 그대로 늘리면 각 worker가 카메라/Hailo를
   중복 점유할 수 있다. 단일 추론 소유권과 IPC 분리 전에는 다중 worker 금지.
4. MJPEG는 장기 연결을 차지하므로 API 응답용 여유, 연결 수 제한, 느린 클라이언트
   해제 정책을 함께 검증한다. 웹 서버만 바꿔 인코딩/네트워크 병목이 사라진다고
   기대해서는 안 된다.
5. 장기적으로 일반 영상 전송은 MediaMTX/WebRTC, 개발용 MJPEG는 필요한 화면에서만.

systemd의 기존 `Restart=on-failure`는 유지했다. 공개 운영 인증, 건강 검사 기반 복구,
MQTT 단절 시 이벤트 보존까지 포함한 가용성 검증은 후속 과제다.

## 6. Dahua에서 쓰러진 등록자를 식별하는 확장 (미적용)

가능한 설계는 **Dahua에서 직접 얼굴을 확인하고, 그 얼굴을 포함하는 사람 track에
등록자 정보를 제한된 시간 동안 연결하는 것**이다. 현재 등록한 SFace 템플릿을
재사용하되 카메라별 얼굴 크기·각도·화질에 따른 검증이 필요하다.

카메라모듈에 마지막으로 보였던 이름을 Dahua 사람에게 붙이거나, 두 카메라의
track ID가 같다고 동일인으로 취급해서는 안 된다. 낙상 후 얼굴이 가려질 때는
쓰러지기 직전의 확실한 인식이 있는 경우에만 짧게 유지하고, 추적 재연결/교차/만료 시
`미확인`으로 돌리는 설계가 필요하다. 신원 실패 때문에 낙상 경보를 막지는 않는다.

낙상 경로의 CPU 부하와 오인 식별 위험을 피하려고 이번에는 활성화하지 않았다.

## 7. Tailscale 설치 및 확인

Pi5에 Debian trixie 공식 stable 저장소와 서명 키를 추가하고 Tailscale 1.104.2를 설치했다.
다른 OS 패키지 업그레이드나 Pi4 설치는 수행하지 않았다.
[공식 Linux 설치 문서](https://tailscale.com/docs/install/linux).

로그인은 사용자 브라우저에서 직접 승인했다.

- 장치 이름: `aismarthome-pi5`
- Pi5 Tailscale IPv4: **100.100.207.97**
- Mac: `macbookpro`, `100.77.190.12`
- 상태: Running / online
- Mac으로 Tailscale ping: 직접 연결, 약 14ms (현재 같은 LAN에서 시험)
- Tailscale 주소로 Pi5 `/health`: 정상
- tailscaled 자동 시작, 기존 OpenSSH :22 유지

Mac에서:

```sh
ssh pi@100.100.207.97
```

웹은 Tailscale이 연결된 장치에서 `http://100.100.207.97:8080`을 이용할 수 있다.
기존 SSH 키 또는 계정 암호를 사용한다. `tailscale up --ssh` 기능은 켜지 않았다.
현재 명령은 `--accept-dns=false --accept-routes=false`였으며 기존 DNS, 카메라 LAN,
Pi4 MQTT 주소를 바꾸지 않았다. 서브넷 라우터·exit node·공유기 포트포워딩도 미설정.

외부망에서의 Mac→Pi5 실제 SSH 로그인은 사용자가 추가로 확인해야 한다.
이번 ping 결과는 외부망 성능 보증이 아니다. 이 구성만으로 Pi4나 Dahua에 외부에서
직접 접속할 수 있게 되는 것도 아니다.

## 8. 검증 / 남은 확인

- Python 회귀 테스트 82개 통과. 최근 중복 방지 기록의 256개 제한, MQTT 제한/거부
  계수 및 거울 방향 매핑을 포함한다.
- Chromium: 탭·거울 안내·등록 취소·시스템 테마 반응·수동 테마 새로고침 유지,
  390px 가로 넘침 없음, 키보드 전환, JavaScript 오류 없음.
- 실제 영상 연결 수가 탭별로 2→1→0이 되는 것을 서버 API에서 확인.
- 얼굴 DB를 수정하거나 실제 낙상 MQTT 시험 이벤트를 생성하지 않았다.
- 장시간 메모리 추이, 실제 얼굴 구도에서의 좌우 안내, 다른 네트워크에서 SSH 로그인은
  현장 확인 대상으로 남는다.
- 이전 작업과 이번 변경은 작업 트리에 있으며 별도 GitHub push는 수행하지 않았다.
